라멘교 자동 모델링은 Revit 애드인이다. 도로 선형과 단면 치수를 입력하면 슬래브부터 날개벽, 접속슬래브까지 라멘교 한 동을 3D 모델로 만들어 준다.

이 글은 기능 소개보다 **만드는 과정**에 대한 기록이다. 2025년 4월에 시작한 이 기능은 코드 구조가 크게 세 번 바뀌었다. 파일을 한 폴더에 몰아 두던 시기, 종류별 폴더로 나누던 시기, 그리고 MVVM을 바탕으로 나름의 틀을 세운 지금. 구조가 바뀔 때마다 계기는 같았다. 코드를 고치기가 점점 어려워졌고, 그때마다 "왜 어려운가"를 먼저 물었다.

## 교량을 부재로 쪼개기

라멘교를 한 덩어리로 보면 어디서부터 손대야 할지 알 수 없었다. 그래서 코드를 쓰기 전에 교량을 부재 단위로 나눴다.

- **상부**: 슬래브, 포장, 방호벽
- **하부**: 교대, 기초(버림콘크리트·말뚝), 교각
- **부속**: 날개벽, 접속슬래브

첫 커밋들은 기초 하나를 만드는 데서 시작했다. 기초가 나오면 버림콘크리트를, 그다음은 교각, 그다음은 날개벽을 만들었다. 한 번에 하나씩, 앞의 것이 확실히 나온 뒤에 다음으로 넘어갔다.

## 모든 부재는 '단면 + 경로'였다

부재를 늘어놓고 보니 공통점이 보였다. 모양은 제각각이지만 거의 모든 부재가 **2D 단면을 경로를 따라 밀어낸 솔리드**였다. 슬래브와 방호벽은 선형 전체를 따라가고, 교대는 시점과 종점에, 교각은 지정한 위치에 놓인다.

이 패턴을 알아챈 뒤로는 풀어야 할 문제가 바뀌었다. "부재 8개를 만든다"가 아니라 두 가지 질문에 답하면 됐다.

1. 단면을 정확히 그릴 수 있는가
2. 그 단면을 어디에, 어느 방향으로 놓는가

이 구분은 나중에 구조를 새로 짤 때 뼈대가 됐다. 단면을 그리는 코드(`ProfileFactory`)와 위치·방향을 계산하는 코드(`AlignmentBasis`)를 따로 두게 된 것이다.

## 막히면 가장 단순한 경우로

날개벽이 가장 어려웠다. 교대 끝에서 비스듬히 뻗어 나가는 벽인데, 날개벽 각도와 Skew(교량이 도로와 비스듬히 만나는 각도), 시점과 종점이 한꺼번에 얽히자 결과가 계속 엉뚱한 방향으로 나왔다. 결국 코드가 너무 엉켜 더 진행할 수 없게 됐고, 이전 파일로 돌아가 브랜치를 새로 팠다.

다시 시작할 때는 변수를 하나씩만 풀었다.

1. 날개벽 각도가 **0°일 때**만 먼저 맞춘다.
2. **0°~180°** 사이와 **180°**인 경우로 넓힌다.
3. **시점** 날개벽을 완성한다.
4. 같은 규칙을 **종점**에 적용한다.

한 번에 하나만 바뀌니 틀렸을 때 어디가 틀렸는지 바로 보였다. 일주일이 안 되어 시점과 종점 날개벽이 모두 나왔다. 이때 "큰 문제를 가장 단순한 경우로 줄여서 풀고, 조건을 하나씩 늘린다"는 방식이 몸에 붙었다.

## 첫 번째 틀: 폴더로 정리하기

초기에는 모든 파일이 폴더 하나에 평평하게 놓여 있었다. 파일이 늘어 찾기가 어려워지자 종류별로 나눴다.

- `Class/`: 교각, 날개벽 같은 데이터 클래스
- `Library/`: 메시지 창, 단위 변환, 형상 유틸리티
- `Extensions/`: Revit 타입에 붙이는 확장 메서드

정리가 된 것 같았지만 곧 한계가 드러났다. 폴더는 **파일이 어디 있는지**는 알려 줬지만 **누가 무엇을 책임지는지**는 알려 주지 않았다. 부재가 늘수록 형상 계산은 `RahmenModel.cs` 하나에 1,854줄, 화면 로직은 `ViewModel.cs` 하나에 2,247줄로 불어났다. 날개벽 하나를 고치려 해도 두 파일을 오가야 했고, 무엇을 고치면 어디까지 영향이 가는지 예측하기 어려웠다.

## MVVM: 파일이 아니라 방향을 나누다

그 무렵 WPF를 쓰면서 MVVM 패턴을 알게 됐다. 화면(View)은 보여 주기만 하고, 화면의 상태는 ViewModel이 들고, 실제 일은 Model이 한다. View와 ViewModel은 데이터 바인딩으로만 연결된다.

바로 라멘교에 적용하지는 않았다. 2,000줄이 넘는 코드에 처음 배운 패턴을 입히면, 문제가 생겼을 때 패턴 탓인지 기존 코드 탓인지 구분할 수 없을 것 같았다. 그래서 규모가 작은 "이름 일괄 변경" 기능에 먼저 적용해 보고, 구조가 비슷한 암거 기능으로 넓혔다. 거기서 감을 잡은 뒤에 라멘교로 돌아왔다.

MVVM에서 얻은 가장 큰 것은 폴더 이름이 아니라 **의존의 방향**이었다. View는 ViewModel만 알고, 형상을 만드는 코드는 화면을 모른다. 의존이 한쪽으로만 흐르게 정하자 새 파일을 어디에 둘지가 저절로 정해졌다.

## 두 번째 틀: 입력에서 모델까지 한 방향으로

MVVM을 기준으로 삼되, 라멘교에 맞게 층을 더 나눴다.

- **View**: 입력창. 값을 보여 주고 받기만 한다.
- **ViewModels**: 입력값과 화면 상태. 부재별로 나눴다.
- **Core**: 생성 직전에 고정한 입력값(`RahmenSpec`), 부재별 파라미터, 유효성 검사
- **Data**: 설정을 저장하고 불러오기 위한 DTO와 매퍼
- **Domain**: 선형 기준(`AlignmentBasis`)과 부재 8개
- **Services**: 단면 생성, 선형 연장 같은 공통 계산
- **Pipeline**: 부재들을 차례로 불러 Revit에 실제로 만드는 곳

생성 버튼을 누르면 흐름은 언제나 같다.

1. **검증**: 폭, 반지름처럼 형상이 성립하지 않는 값이 있는지 먼저 본다.
2. **스냅샷**: 화면 값을 `RahmenSpec`으로 떠 둔다. 생성 도중 화면 값이 바뀌어도 결과는 흔들리지 않는다.
3. **기준 계산**: 선형의 시점·종점, 접선, 좌우 방향을 한 번만 계산한다.
4. **부재 생성**: 부재마다 단면을 만들고 솔리드를 쌓는다.
5. **배치**: 하나의 트랜잭션 안에서 Revit 요소로 만들고, 결과를 상태줄에 남긴다.

두 파일에 몰려 있던 코드는 이제 역할별로 51개 파일에 나뉘어 있다.

## 각 부분이 알아야 할 것을 줄이기

구조를 짜면서 가장 신경 쓴 것은 **각 부분이 알아야 할 것을 최소로 줄이는 것**이었다.

- **같은 약속**: 모든 부재는 `IRahmenComponent`라는 같은 인터페이스를 따른다. 이름, 생성 여부, 형상을 돌려주는 `BuildGeometry` 하나가 전부다. 파이프라인은 지금 부르는 것이 슬래브인지 날개벽인지 모른 채 차례로 부를 뿐이다. 부재가 하나 늘어도 파이프라인에는 한 줄만 추가된다.
- **기준은 한 곳에서**: 예전에는 접선과 Skew 평면 같은 기준값이 부재 생성 코드와 한 클래스에 섞여 있어서, 어떤 값이 언제 계산되는지 따라가기 어려웠다. 지금은 `AlignmentBasis`가 한 번 계산하고 모든 부재가 가져다 쓴다. 좌우 방향 벡터는 **Skew 적용 여부**와 **횡단 경사 적용 여부**라는 두 요인으로 나눠 보니 네 가지 조합으로 정리됐다. 부재는 필요한 조합을 고르기만 하면 된다.
- **버튼은 조합일 뿐**: 전체 생성, 횡단면 생성, 교대·기초·교각·날개벽 생성 버튼마다 코드를 따로 두지 않았다. 부재 하나에 비트 하나를 준 `BuildOptions`를 만들고, 각 버튼은 그 비트들의 조합으로 표현했다.

## 옛 코드 옆에 새 코드를 쌓기

리팩토링은 한 번에 갈아엎지 않았다. 기존 라멘교 기능은 이미 쓰이고 있었기 때문에, 옛 코드는 그대로 두고 그 옆에 새 구조(`NewRahmen`)를 만들었다.

옮기는 순서는 처음 교량을 쪼갰던 순서를 그대로 따랐다. 슬래브·포장 → 방호벽 → 교대 → 기초 → 헌치·브라켓 → 교각 → 날개벽 → 말뚝 → 접속슬래브. 부재 하나가 새 구조에서 제대로 나와야 다음 부재로 넘어갔고, 전부 옮긴 뒤에야 옛 폴더를 지웠다. 2025년 10월 말에 시작해 12월에 교체를 마쳤고, 이후 이름에서 `New`를 떼어 지금의 `Rahmen`이 됐다.

말뚝과 접속슬래브는 옛 코드에 없던 부재였다. 새 구조에서는 컴포넌트를 하나씩 추가하는 것으로 끝났다.

## 구조 위에 기능을 얹기

틀이 잡히자 기능을 붙이는 방식이 달라졌다. 새 요구가 들어오면 먼저 "어느 층의 일인가"를 정했다.

- **재질 입력**: 부재별 파라미터에 재질을 추가하고, 각 컴포넌트가 솔리드를 만들 때 그 값을 쓰게 했다. 화면과 형상 코드가 분리돼 있어서 포장 → 슬래브 → 방호벽 → 교대 → 기초 → 교각 → 날개벽 순으로 하나씩 붙여 나갈 수 있었다.
- **설정 저장**: 레지스트리에 흩어져 있던 입력값을 DTO 하나로 모아 JSON 파일로 저장하게 했고, 내보내기와 가져오기도 붙였다. 화면(ViewModel)과 저장 형식(DTO) 사이에 매퍼를 두어 한쪽을 바꿔도 다른 쪽은 건드리지 않게 했다.
- **실패 격리**: 예전에는 한 부재에서 예외가 나면 그 뒤 부재들이 아예 만들어지지 않았다. 지금은 파이프라인이 부재마다 따로 실행하고, 실패는 모아 두었다가 마지막에 한 번만 알린다. 그다음에는 단위를 더 잘게 쪼개서, 날개벽 4개 중 1개나 교각 여러 개 중 1개가 실패해도 나머지는 만들어지게 했다.
- **치수 0의 의미**: 헌치나 브라켓 치수에 0을 넣으면 오류가 나던 것을 "그 형상이 없다"는 뜻으로 해석하게 바꿨다. 입력값이 설계에서 무엇을 뜻하는지부터 다시 정의한 것이다.
- **이름 규칙**: 생성되는 요소마다 부재, 세부부재, 위치, 순번을 조합한 이름을 붙였다. 나중에 수량을 산출할 때 이름만 보고 무엇인지 알 수 있게 하려는 준비다.

## 버그를 규칙으로

Revit 안에서 도는 WPF는 작은 실수 하나로 Revit 전체를 강제 종료시킨다. 한번은 라디오 버튼을 누르면 Revit이 바로 꺼지는 문제가 있었다. 원인을 따라가 보니 WPF의 `GroupName`과 ViewModel의 파생 속성이 서로를 계속 갱신하며 StackOverflow에 빠진 것이었다.

그 자리만 고치고 끝내지 않았다. "라디오 버튼에는 `GroupName`을 쓰지 않고, 컨버터와 ViewModel에서 상호 배타를 처리한다"는 규칙을 정하고, 라멘교의 라디오 그룹 전부를 같은 방식으로 바꿨다. 한 번 겪은 문제를 한 곳의 수정이 아니라 전체의 규칙으로 바꾸는 것도 구조를 지키는 일이라고 생각한다.

## 돌아보며

처음 목표는 "라멘교가 나오게 하는 것"이었다. 지금의 목표는 "부재 하나를 고쳐도 다른 부재가 흔들리지 않는 것"이다.

폴더에서 MVVM으로, MVVM에서 지금의 파이프라인으로 옮겨 올 때마다 계기는 같았다. 고치기 어려워졌다는 불편함이다. 그 불편을 그냥 넘기지 않고 "왜 어려운가"를 물었을 때 다음 구조가 보였다.

이 틀은 라멘교에서 끝나지 않았다. 암거 기능도 같은 흐름(입력 → 스펙 → 기준 → 부재 → 파이프라인)을 쓰고, 두 기능이 함께 쓰는 인터페이스와 결과 형식은 `Shared` 폴더로 모았다.
